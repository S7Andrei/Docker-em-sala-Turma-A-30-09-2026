Na primeira execução, os containers da API e do portal já estavam ativos. A página principal retornou HTTP 200, mas as rotas `/api/saude` e `/api/eventos` retornaram HTTP 502. Os logs mostraram que a API iniciou na porta 5000, enquanto o Compose estava configurado para a porta 4000. 
Também identifiquei que `API_URL` apontava para `localhost:4000`, que não funcionava como endereço da API dentro do container do portal. Ajustei o endereço para `http://api:4000`, alterei a variável `PORT` para `4000` e adicionei o volume `registros` para manter as inscrições salvas após a recriação dos containers. 
Descartei a hipótese de problema no catálogo, pois o arquivo `dados/eventos.json` continha os três eventos e a API respondia normalmente em `/saude`. Após as alterações, confirmei que as rotas funcionavam pelo portal, enviei uma inscrição de teste e recebi HTTP 201. O primeiro evento passou a ter 1 inscrito e 11 vagas restantes. 
Depois de executar `docker compose down` e `docker compose up -d`, a inscrição continuou salva. Por fim, confirmei que somente o portal publicou a porta `127.0.0.1:8082` no computador, sem expor a porta da API.
